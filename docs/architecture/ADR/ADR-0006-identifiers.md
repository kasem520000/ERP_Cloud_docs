# ADR-0006 — UUIDv7 Technical IDs + Separate Official Document Numbering

> **Status:** ACCEPTED · **Date:** 2026-10-27 · **Supersedes:** none

## Context

The Platform must support offline-created entities (POS sales on a disconnected
terminal, field-sales drafts on a phone), multi-device merge, and idempotent retries,
while also producing human-readable, legally meaningful document numbers per tenant
(e.g., sequential invoice numbers that jurisdictions expect, without gaps introduced by
concurrent devices).

## Decision

Two distinct identifier systems with different policies:

1. **Technical primary keys: UUIDv7** (`uuid` columns, generated by the application via
   the shared kernel; time-ordered for index locality). Client-generated for
   offline-capable entities → server upserts by ID with idempotency keys; no
   auto-increment anywhere in tenant data.
2. **Official document numbers: per-tenant (and per-branch where configured) named
   sequences** with a numbering format (e.g., `INV-{BRANCH}-{YYYY}-{seq:6}`), assigned
   by the server **at approval/issuance time**, immutable afterwards. Sequences are
   PostgreSQL sequences or a numbering table with row locks; number assignment happens
   in the same transaction as the document's state change.
3. Numbering gaps are permitted **only** through documented paths: voided reserved
   numbers (kept with the document for audit), sequence resets by policy. No
   re-numbering, ever.

### Why not

| Alternative | Why not |
|-------------|---------|
| BIGSERIAL PKs | Server-roundtrip required for every insert (breaks offline creation); cross-tenant sequence contention; leaks volume information in URLs. |
| UUIDv4 PKs | Random UUIDs fragment B-tree indexes at scale; no temporal locality. |
| Reusing official numbers as PKs | Couples legal numbering to database identity; renaming/reformat policies become impossible; offline assignment would break uniqueness. |

## Consequences

- Offline clients generate UUIDv7 IDs locally; sync deduplicates by ID + idempotency key
  ([ADR-0012](ADR-0012-offline-sync.md)).
- Official numbers remain dense, auditable, and jurisdiction-friendly even when documents
  originate offline — numbers are assigned only on the server at finalization
  (POS offline sales use a documented offline receipt-number scheme reconciled to the
  official sequence; see [../../offline/SYNC_PROTOCOL.md](../../offline/SYNC_PROTOCOL.md)).
- URLs/logs carry UUIDs (no info leak); printed documents carry official numbers.
- Every entity catalog entry states whether the entity is **offline-creatable**
  ([../../database/ENTITY_CATALOG.md](../../database/ENTITY_CATALOG.md)).

## Revisit triggers

- If a jurisdiction mandates a specific numbering integration (e.g., authority-issued
  UUID/ICV in e-invoicing), it is layered INTO the document's compliance payload —
  the two-system rule stays intact.
